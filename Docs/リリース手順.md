前提: Apple Developer Program（有料）への加入。

## 1. 一度だけ行う準備

### 1-1. Sparkle 署名鍵

Sparkle は appcast（更新情報）を EdDSA 署名で検証する。公開鍵をアプリに埋め込み、秘密鍵で CI が署名する。

鍵は **JPAgentManager 専用**で、この Mac のログインキーチェーンの account `JPAgentManager` にある。JPScreenShot の鍵とは別。appcast の署名鍵はアプリ単位で分けておくと、片方が漏れたときの影響範囲を切り離せる。

公開鍵は [App/Info.plist](../App/Info.plist) の `SUPublicEDKey` に入っている。

CI 用に秘密鍵を書き出して Secret に登録する（Sparkle 2.9.3 の配布物に入っている `generate_keys` を使う）。**書き出し物は必ず一時フォルダで扱う**。リポジトリ直下で実行すると、秘密鍵や配布物が公開リポジトリに入りうる。

```sh
tmp="$(mktemp -d)" && cd "$tmp"
curl -fL -o sparkle.tar.xz \
  https://github.com/sparkle-project/Sparkle/releases/download/2.9.3/Sparkle-2.9.3.tar.xz
mkdir sparkle-tools && tar -xf sparkle.tar.xz -C sparkle-tools

# 公開鍵を表示し、App/Info.plist の SUPublicEDKey と一致するか確かめる
./sparkle-tools/bin/generate_keys --account JPAgentManager -p
./sparkle-tools/bin/generate_keys --account JPAgentManager -x key.txt    # 秘密鍵を書き出す
gh secret set SPARKLE_PRIVATE_KEY --repo Junpeiwada/JPAgentManager < key.txt
cd - && rm -rf "$tmp"                                                    # 登録したら消す
```

> ⚠️ 書き出した秘密鍵ファイルは**リポジトリにコミットしない**。Secret 登録後は必ず削除する（原本はキーチェーンに残る）。
> **鍵を失うと、既に配った版は以後の更新を受け取れない。** キーチェーンの原本を消さない。

### 1-2. Developer ID 証明書

Mac App Store 外で配布するには **Developer ID Application** 証明書が必要。**同一チームの既存証明書をそのまま流用できる**（アプリごとに取り直すものではない）。

```
Developer ID Application: Junpei Wada (L897K2C26B)   ← 配布・公証用
```

CI へ渡すには `.p12` 形式の Base64 を Secret にする:

```sh
base64 -i <証明書>.p12 | gh secret set DEVELOPER_ID_CERT_P12 --repo Junpeiwada/JPAgentManager
```

> 実物は手元の保管場所にある `.p12` とそのパスワード（保管場所は公開リポジトリに書かない）。

### 1-3. 公証用 App Store Connect API キー

`notarytool` はパスワード方式より API キー方式が安定。**API キーはチーム単位**で、Mac App Store 外配布なら App Store へのアプリ登録は不要。JPScreenShot 用に作ったキーをそのまま使える。

- `.p8`: 手元の保管場所にあるもの（場所は公開リポジトリに書かない）。登録は `base64 -i <AuthKey>.p8 | gh secret set ASC_API_KEY_P8 --repo Junpeiwada/JPAgentManager`
- Key ID: `.p8` と対になる値（手元の記録から。値は公開リポジトリに書かない）
- Issuer ID: [App Store Connect → Integrations → API](https://appstoreconnect.apple.com/access/integrations/api) の画面上部の UUID

> `.p8` は**ダウンロードが一度きり**。紛失したら再作成になる。
> **Issuer ID はチーム共通の値**で `.p8` には含まれず、**どこからも複製できない**（GitHub Secrets は登録後に値を読み出せない）。上の画面から取り直す。

### 1-4. GitHub Secrets

**GitHub Secrets はリポジトリ間で値を複製できない。** JPScreenShot に登録済みでも、JPAgentManager に改めて登録が要る。

**Settings → Secrets and variables → Actions** で登録する。`gh secret set <名前> --repo Junpeiwada/JPAgentManager` でもよい。

| Secret 名 | 中身 | 出どころ | 状態 |
|---|---|---|---|
| `TEAM_ID` | `L897K2C26B` | Apple Developer のチーム ID | ⬜ |
| `DEVELOPER_ID_CERT_P12` | `.p12` の Base64 | 手元の保管場所の `.p12` | ⬜ |
| `DEVELOPER_ID_CERT_PASSWORD` | `.p12` のパスワード | 手元の保管場所 | ⬜ |
| `ASC_API_KEY_P8` | `.p8` の Base64 | 手元の保管場所の `.p8` | ⬜ |
| `ASC_KEY_ID` | `.p8` の Key ID | 手元の記録 | ⬜ |
| `ASC_ISSUER_ID` | Issuer ID（UUID） | App Store Connect の Integrations → API 画面上部 | ⬜ |
| `SPARKLE_PRIVATE_KEY` | Sparkle 秘密鍵 | 1-1 の書き出し | ⬜ |

`GITHUB_TOKEN` は GitHub が自動発行するので登録不要。

確認:

```sh
gh secret list --repo Junpeiwada/JPAgentManager | wc -l   # 期待: 7
```

### 1-5. GitHub Pages を有効化する

appcast の配信先。**`gh-pages` ブランチは初回リリースのワークフローが自動生成する**ので、この設定は初回リリース後に行う。

1. **Settings → Pages** を開く
2. **Source** を `Deploy from a branch`、**Branch** を `gh-pages`、フォルダ `/ (root)`
3. 公開 URL は `https://junpeiwada.github.io/JPAgentManager/`

置くのは `appcast.xml` だけで、ランディングページは置かない。この URL が [App/Info.plist](../App/Info.plist) の `SUFeedURL`（`.../appcast.xml`）と一致していること。**一致しないと自動更新が動かない。**

## 2. リリースを発行する（毎回）

準備が済んでいれば、次の 1 コマンドで完結する。

```sh
Scripts/release.sh 0.1.1        # 確認プロンプトあり
Scripts/release.sh 0.1.1 -y     # 確認なしで発火
Scripts/release.sh --help
```

[Scripts/release.sh](../Scripts/release.sh) は次をまとめて行う。

1. [project.yml](../project.yml) の `MARKETING_VERSION` を上げてコミット
2. タグ `v0.1.1` を打つ
3. 今いるブランチ（通常は main）とタグを `git push --atomic` で 1 回で push（これで CI が走る）

実行前に、origin より遅れていないかを確かめる。ワーキングツリーが汚れている／タグが既存／origin より遅れている／`MARKETING_VERSION` の置換が空振りした場合は、安全のため中断する。手で行うなら `git tag v0.1.1 && git push origin v0.1.1`（`project.yml` の `MARKETING_VERSION` は記録のために自分で上げる）。

手動実行（workflow_dispatch）では、入力した版（`X.Y.Z` 形式でないと失敗）でタグ `v<版>` が、ビルドしたコミット（実行したブランチの先頭）に作られる。

### VSCode の NPM SCRIPTS から実行する

[package.json](../package.json) にスクリプトを登録してあるので、VSCode の **NPM SCRIPTS** パネル（エクスプローラの下部）からクリックで実行できる。`npm run <名前>` でも同じ。

| スクリプト | 内容 |
|---|---|
| `release` | リリースを発火（版は対話で尋ねる。パッチを +1 した値が既定） |
| `generate` | `xcodegen generate` |
| `build` | 生成 → Debug ビルド（出力は `build/`） |
| `test` | 生成 → テスト |
| `run` | ビルド済みの `.app` を起動 |
| `sample` | ビルド済みの `.app` を `--sample`（サンプルデータ）で起動 |

```sh
npm run release -- 0.1.1      # 版を渡して発火
npm run release               # 引数なし。端末なら版を対話で尋ねる
```

> パネルからクリックで実行すると引数を渡せないので、版を指定しないときは端末で対話入力を求める。
> `package.json` は**この用途のためだけに置いている**（アプリ本体は Swift/Xcode で、npm の依存はない）。

### 発行後の確認

- Actions の `Release` が成功している
- **Releases** に `JPAgentManager-<版>.zip` が添付されている
- `https://junpeiwada.github.io/JPAgentManager/appcast.xml` が最新版を指している
- ダウンロードした `.app` の初回起動で Gatekeeper 警告が出ない（公証・ステープルが効いていれば出ない）
- 旧バージョンのアプリで、パネルのフッターか、メニューバーアイコンの右クリック（control＋クリック）の「更新を確認…」から更新が検出される

## 3. バージョン番号の運用

- 配布物の版（`MARKETING_VERSION`）は、CI がタグから `v` を外した値で上書きして決まる。タグは必ず `v` プレフィックス付き（`v0.1.1`）
- [project.yml](../project.yml) の `MARKETING_VERSION` は、手元のビルドと記録を合わせるために `Scripts/release.sh` が上げるもの。配布物の版は決めない
- Sparkle が新旧を判定する `CFBundleVersion` は、CI が GitHub Actions の run 番号（単調増加）で上書きする。手動管理は不要

## 4. CI が何をしているか

[.github/workflows/release.yml](../.github/workflows/release.yml)（ワークフロー名は `Release`。タグ `v*` の push か手動実行）の流れ。`concurrency`（group: `release`）で同時には走らない。

1. `App/Info.plist` の `SUPublicEDKey` が空なら最初に止める
2. `xcodegen generate` でプロジェクトを生成（`.xcodeproj` は Git 管理外なので必須）
3. Developer ID 証明書を一時キーチェーンへインポート
4. `xcodebuild archive` で Release 構成をアーカイブ（署名は Developer ID）。ハードンドランタイムはコマンドラインで `ENABLE_HARDENED_RUNTIME=YES` を渡して付ける
5. `ExportOptions.plist` で `.app` をエクスポート（Sparkle も再署名される）
6. `notarytool submit --wait` で公証。却下されたら `notarytool log` を出す。通ったら `stapler staple` で結果を添付し、`stapler validate` で確かめる
7. 配布 zip（`JPAgentManager-<版>.zip`）を作り、`generate_appcast` で `appcast.xml` を生成（秘密鍵で署名）。**Release の作成より前**に行う
8. `gh release create` で **GitHub Release を作成**。Release が既にあれば zip を `--clobber` で差し替える（再実行できる）
9. `appcast.xml` だけを **gh-pages へ publish**

Sparkle の版は 2.9.3 に固定（`exactVersion`）。上げるときは [project.yml](../project.yml) と release.yml の `generate_appcast` の版を一緒に上げる。

ランナーは **`macos-26`**。`deploymentTarget: macOS 26.0` をビルドするには macOS 26 SDK が必要なため、`macos-15` では通らない。

## 5. つまずきやすい点

### ハードンドランタイムは CI がコマンドラインで付ける

公証にはハードンドランタイムが必須。[project.yml](../project.yml) では全構成 `NO` にしてあり、CI の `xcodebuild archive` に `ENABLE_HARDENED_RUNTIME=YES` を渡して付ける。アドホック署名のまま有効にすると、Sparkle をライブラリ検証で読めず起動しないため。こうしておけば、ローカルの Release ビルドも起動できる。

### Info.plist の Sparkle 設定

`SUFeedURL`・`SUPublicEDKey`・自動確認（24 時間ごと）は [App/Info.plist](../App/Info.plist) にある。Debug ビルドでは、`SPUUpdaterDelegate` の `mayPerform` が背景の確認（`.updatesInBackground`）だけを止める。設定値は書き換えず、配布版の自動確認には影響しない。手動の「更新を確認…」は Debug でも動く。押すと配布版で自分を置き換えうるので、開発中は押さない。

### jpam-hook はアプリに入らない

`jpam-hook` ターゲットと `HookHelper/` のソースは残っているが、アプリには同梱しない。テストのためだけにビルドされ、テストはビルド成果物の置き場所（アプリと同じフォルダ）から読む。

### Secrets の登録漏れ

Secrets はリポジトリごと。JPScreenShot に入っているからといって JPAgentManager で使えるわけではない。`gh secret list --repo Junpeiwada/JPAgentManager | wc -l` で 7 件あるか先に確かめる。

### 公証は Apple のサーバ待ちで数分かかる

`notarytool submit --wait` はワークフローを止めて完了を待つ。通常は 1〜5 分。混雑時はさらに伸びる。

### appcast が 404 のとき

初回リリース直後は Pages が未設定のため appcast が 404 になる。1-5 を行う。設定しても 404 なら、publish ステップが失敗して `gh-pages` ができていない。Actions のログを確かめる。それまでは「更新を確認…」が「更新情報を取得できない」旨のエラーになるが、想定内。

### release.yml のファイル名は変えない

ファイル名を変えると run 番号（`CFBundleVersion`）が 1 に戻り、Sparkle が新しい版を古いと判断する。
